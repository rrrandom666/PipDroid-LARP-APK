# PipBoy BLE Protocol — v0.2

Заменяет `PipBoy_BLE_Protocol_v0.1.md`. v0.1 был написан под кастомный GATT-сервис с
отдельной характеристикой на каждую подсистему — это **вариант Б**, от него отказались.

Этот документ — **вариант А**: расширение уже существующей архитектуры из репозитория
[Malto4/PipDroid-APK](https://github.com/Malto4/PipDroid-APK), а не проектирование с нуля.
База — рабочий Nordic UART Service (NUS) и уже написанный код обработки `STATS/ITEMS/DATA`
в прошивке (`ESP32_S3_Mini_PythonFiles/main.py`) и в приложении (`MainActivity.kt`,
`menuChangeBLE()`).

---

## 1. Что уже есть — фиксируем как есть, не трогаем без нужды

**Транспорт:** один стандартный Nordic UART Service, а не набор кастомных характеристик.

| | UUID |
|---|---|
| Service | `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` |
| TX (ESP32 → телефон, Notify) | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` |
| RX (телефон → ESP32, Write) | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` |

Весь обмен — обычные ASCII-строки поверх этих двух характеристик, не бинарные структуры.

**Прошивка (`main.py`):**
- Класс `BLESimplePeripheral` определён прямо в файле (не путать с `ble_uart_peripheral.py` —
  тот не используется, это неиспользуемый референс из примеров MicroPython)
- 3 кнопки на GPIO 16/17/18 (`STATS`/`ITEMS`/`DATA`), active-low, `Pin.PULL_UP`
- Главный цикл: опрос каждые 350 мс, при нажатии шлёт строку `"STATS"` / `"ITEMS"` / `"DATA"`
  через `p.send()`. **Важно: это отправка каждый цикл, пока кнопка держится нажатой, а не
  событие "изменилось состояние"** — то есть при удержании кнопки клиент получит несколько
  одинаковых уведомлений подряд. На стороне приложения это не мешает (просто переключает на
  тот же экран повторно), но при добавлении, например, энкодера так делать нельзя — см. раздел 3
- Приём с телефона (`on_rx`) уже реализован на уровне транспорта — записывает пришедшую строку
  в `vars.sentVALUE`, но **никак не используется дальше**. Это точка расширения, а не готовая
  функциональность — сейчас это просто заглушка

**Приложение (`MainActivity.kt`):**
- `BluetoothGattCallback.onCharacteristicChanged` читает строку → `bleMenuChange` →
  `menuChangeBLE(bleMenuChange)`, `when(menu) { "STATS" -> ...; "ITEMS" -> ...; "DATA" -> ... }`
- Пейринг — ручной: MAC-адрес и UUID сервиса/характеристик вводятся текстом в настройках,
  хранятся в `SharedPreferences` (`bluetoothMAC_SPKey`, `bluetoothSUUID_SPKey`,
  `bluetoothRUUID_SPKey`, `bluetoothWUUID_SPKey`). Нет сканирования/списка устройств — это
  и есть текущий "пейринг под BYOD", проще, чем я закладывал в roadmap изначально, но рабочий,
  если на корпус каждого PipBoy нанести MAC стикером/гравировкой
- Путь телефон → ESP32 (`writeCharacteristic()`, `sendBLEText()`) уже написан на уровне
  инфраструктуры, но не факт, что привязан к какому-то реальному действию в UI — надо
  проверить отдельно, не полагаться на предположение

## 2. Конвенция новых команд

Расширяем тот же плоский текстовый протокол, а не переходим на бинарный формат.

- Команды без параметров — просто ключевое слово, как уже есть (`STATS`, `ITEMS`, `DATA`)
- Команды с параметром — `КЛЮЧ:ЗНАЧЕНИЕ`, разделитель `:`, парсинг — `split(":")`,
  первый токен — команда, остальное — payload
- Регистр — всегда UPPERCASE (следуем уже заданному стилю `STATS`/`ITEMS`/`DATA`)
- Направление не кодируется в самой строке (в отличие от bin-протокола v0.1) — совпадающие
  по смыслу команды в разные стороны различаются по тому, кто их шлёт, не по имени

## 3. Новые команды

### ESP32 → телефон (Notify по TX)

| Команда | Когда шлётся | Пример |
|---|---|---|
| `STATS` / `ITEMS` / `DATA` | уже есть, без изменений | `STATS` |
| `POWER:<0/1>` | нажатие кнопки Power **и** повторно при каждом реконнекте — см. раздел 3.1 | `POWER:1` |
| `ENCBTN` | нажатие кнопки энкодера | `ENCBTN` |
| `ENC:<±N>` | поворот энкодера, шлётся **по изменению**, не по опросу — см. раздел 5 | `ENC:+1`, `ENC:-2` |
| `GEIGER:<0-255>` | по циклу Wi-Fi-скана (~раз в 6 сек, см. roadmap) | `GEIGER:140` |
| `HOLOTAPE:1` / `HOLOTAPE:0` | вставлен/вынут голодиск | `HOLOTAPE:1` |
| `RADIOFREQ:<число>` | подтверждение фактически настроенной частоты (МГц×10) | `RADIOFREQ:998` |
| `RADIOPWR:<0/1>` | переключение физического тумблера радио **и** повторно при реконнекте — см. раздел 3.2 | `RADIOPWR:1` |
| `RADIOTUNE:<±N>` | поворот радио-энкодера в режиме тюнинга — см. раздел 3.3 | `RADIOTUNE:+1` |
| `VOLUME:<±N>` | поворот радио-энкодера в режиме громкости — см. раздел 3.3 | `VOLUME:-1` |
| `RADIOTUNEBTN` | нажатие кнопки радио-энкодера — переключает режим тюнинг/громкость | `RADIOTUNEBTN` |

### 3.1 Логика POWER — ESP32 как хозяин состояния

Кнопка POWER — не рядовая кнопка меню, а переключатель состояния всего устройства. Надёжно
"запустить убитое приложение по BLE-событию" на Android для BYOD-парка телефонов недостижимо:
единственный штатный механизм (`CompanionDeviceManager` presence-wake из killed-состояния)
работает только с API 33+, а у нас `minSdk 19` и заведомо разные версии Android у игроков.
Поэтому включение/выключение — **симуляция на стороне приложения** (état-машина, раздел 5),
а не реальный старт/стоп процесса: PipDroid работает постоянно, "выключенный" PipBoy — это
чёрный экран внутри работающего приложения, не остановленное приложение.

Отсюда правило: **источник истины по физическому состоянию — ESP32, не телефон.** Подсветка
корпуса не должна зависеть от того, жив ли в данный момент BLE-коннект.

Порядок действий по нажатию кнопки POWER на ESP32:
1. Переключить локальный флаг `powerState = not powerState`
2. **Немедленно**, не дожидаясь ничего от телефона, применить его к физической подсветке,
   которой управляет сам ESP32: лампы накала, подсветка кнопок STATS/ITEMS/DATA/POWER,
   подсветка циферблата вольтметра Гейгера, подсветка шкалы радио
3. Только после этого отправить `POWER:1` / `POWER:0` в TX. Если телефон в этот момент не
   подключён, notify просто не уйдёт — это нормально, подсветка уже переключилась независимо
   от связи

Это разрывает зависимость "видимая жизнь корпуса" от стабильности BLE на носимом устройстве
(разрывы уже зафиксированы как неизбежные, см. Phase B roadmap).

**Ресинхронизация при реконнекте:** приложение не должно ждать нового нажатия кнопки, чтобы
узнать текущее состояние после разрыва связи. По событию `_IRQ_CENTRAL_CONNECT` ESP32 сразу
шлёт актуальный `POWER:<state>` (не только по факту нажатия) — приложение обязано применить
его как есть (не тумблерить относительно предыдущего локального состояния).

**Состояние по умолчанию до первого `POWER` от ESP32** (холодный старт приложения, ещё не
было ни одного пуша): экран чёрный (OFF) — безопасный дефолт.

Открытый вопрос: сейчас POWER — это только короткое нажатие (tap-toggle). Различение
короткого/долгого нажатия (например, долгое — на будущее для аварийного сброса) не
реализуется, не блокирует текущую логику.

### 3.2 Логика радио — тумблер как хозяин состояния (по аналогии с 3.1)

Основной способ включить/выключить радио — физический тумблер (GPIO 15), не команда из
приложения. Та же схема, что и у POWER: ESP32 сразу, локально, независимо от BLE, включает/
выключает RDA5807M по I2C, и только потом шлёт `RADIOPWR:<state>` в TX. Ресинхронизация при
реконнекте — так же, повторная отправка текущего состояния по `_IRQ_CENTRAL_CONNECT`.

На стороне приложения: получен `RADIOPWR:1` → переключиться на экран радио. На `RADIOPWR:0` —
**остаться на текущем экране**, только обновить статус радио (не уводить пользователя никуда:
при выключении радио неизвестно, куда он хочет перейти дальше).

Существующая команда `RADIOPWR:1/0` в направлении телефон → ESP32 (раздел ниже) остаётся в
протоколе как есть — её соотношение с физическим тумблером (приоритет, дублирование или
что-то ещё) сознательно не решается сейчас, отложено.

### 3.3 Тюнинг радио — отдельный физический энкодер, режимы тюнинг/громкость

**Физическое ограничение важнее программного удобства:** тюнинг радио идёт через **отдельный
тумблер игровой модели** (LARP-реквизит копирует конкретное устройство из игры, форму менять
нельзя) — переиспользовать пины/железо основного энкодера меню нельзя, это должен быть второй,
физически отдельный узел на корпусе.

Механизм — **энкодер, не потенциометр**: реализация повторяет уже написанный decode для
энкодера меню (раздел 4, прерывания + таблица переходов + накопление четверть-шагов), просто
на других GPIO — экономит время разработки и не требует ADC/калибровки аналогового сигнала.
Заодно RDA5807M сам хранит частоту пошагово (типично шаг 50/100 кГц), так что "континуальность"
потенциометра всё равно была бы иллюзией на уровне регистра чипа — разницы в ощущениях у
игрока нет.

**Совмещение с громкостью:** у энкодера три сигнала (A/B/SW) — третий, кнопка, не тратится
впустую. ESP32 хранит локальный флаг режима (`tuneMode`, по умолчанию тюнинг), переключаемый
нажатием `RADIOTUNEBTN`. Вращение энкодера в режиме тюнинга шлёт `RADIOTUNE:±N` (шаг частоты),
в режиме громкости — `VOLUME:±N`. Само нажатие `RADIOTUNEBTN` тоже уходит в TX, чтобы
приложение при желании показало индикатор текущего режима.

GPIO (см. полную карту в разделе 4.0): Radio Tune A — 33, Radio Tune B — 34, Radio Tune SW — 35.

`RADIOFREQ:<число>` (подтверждение фактической частоты) не меняется — совместим с любым
механизмом ввода. Строка "Тумблер переключения радиоволн" в BOM (`PipBoy_Roadmap.md`)
заменена на второй энкодер.

### Телефон → ESP32 (Write по RX)

| Команда | Действие на ESP32 | Пример |
|---|---|---|
| `RADIOPWR:1` / `RADIOPWR:0` | вкл/выкл RDA5807M | `RADIOPWR:1` |
| `RADIOFREQ:<число>` | настроиться на частоту (МГц×10) | `RADIOFREQ:1021` |
| `HOLOTAPE:LIST` | запросить список файлов на флешке | `HOLOTAPE:LIST` |
| `HOLOTAPE:READ:<n>` | запросить чтение файла номер `n` | `HOLOTAPE:READ:2` |

**Голодиск, как и в v0.1, остаётся самым сырым местом** — передача содержимого файла
(`holotape_data`, множественные чанки) поверх одной TX-характеристики потребует либо
разбивки на пронумерованные строки (`HOLOTAPE:DATA:0:первые20байт`, `HOLOTAPE:DATA:1:...`),
либо переключения именно этого потока на бинарный формат поверх той же характеристики.
Решать после реального теста throughput в Phase A — сейчас формат ниже условный.

## 4. Что нужно добавить в прошивку (`main.py`)

### 4.0 Плата и карта GPIO (зафиксировано)

**Плата:** `ESP32-S3-DevKitC-1` (модуль **WROOM-1**, как и планировалось изначально в
roadmap) — полноразмерная плата с официальной, задокументированной распиновкой, а не
компактный клон. Причина: проекту нужно одновременно занять ~13 линий (кнопки, энкодер,
I2C, несколько ШИМ-каналов) плюс зарезервировать нативный USB под USB Host для голодиска —
на безымянных "mini"-клонах меньше выведенных на гребёнку GPIO и не всегда есть надёжная
распиновка, на которую можно свериться перед пайкой. **Важно:** папка
`ESP32_S3_Mini_PythonFiles` — легаси-название, оставшееся от форкнутого проекта, к выбору
платы отношения не имеет; сам код (`main.py`, класс `BLESimplePeripheral`) от платы не зависит
и переносится как есть.

На WROOM-1 диапазон GPIO 26–32 всегда занят внутри модуля под флеш — не трогать. Диапазон
33–37 (занят только на WROOM-2 с восьмислойной PSRAM) на WROOM-1 свободен и доступен под
будущие нужды (например, I2S для основного динамика, если этот тракт решат вести через
ESP32, см. открытый вопрос ниже). Strapping-пины 0/3/45/46 и USB D+/D- 19/20 — как и
раньше, зарезервированы.

Основной динамик (не пьезо) в карту не включён — не решено, идёт ли этот звуковой тракт
через ESP32 (тогда потребуется I2S, GPIO из резерва) или звук берётся с самого телефона.
Отдельное архитектурное решение, не блокирует текущую прошивку.

- **Реализовать POWER по логике раздела 3.1**: локальный флаг состояния, немедленное
  управление подсветкой (лампы, кнопки, циферблаты) независимо от статуса BLE-соединения,
  затем notify `POWER:<state>`. Отдельно повесить повторную отправку `POWER:<state>` на
  обработчик `_IRQ_CENTRAL_CONNECT` — реконнект должен ресинхронизировать телефон без
  нового нажатия кнопки
- **Реализовать RADIOPWR по логике раздела 3.2** — тот же паттерн, что и POWER (локально
  → I2C в RDA5807M → notify → resend на реконнект), GPIO 15
- **Лампы накала (GPIO 13) — программный fade, не мгновенный ШИМ-скачок.** В отличие от
  подсветки кнопок (GPIO 12, простой вкл/выкл), при переключении `powerState` яркость ламп
  должна плавно нарастать/спадать (имитация разогрева нити накала) — например, LEDC-таймер,
  который на каждом шаге увеличивает/уменьшает duty cycle с небольшим интервалом, а не
  установка целевого значения одной командой. **Другой логики у ламп нет и не планируется** —
  только это включение/выключение по POWER, никакой независимой регулировки яркости с
  телефона (команда `LAMP:<0-255>` из более раннего черновика протокола убрана как
  неиспользуемая — реального сценария под неё не было)
- **Убрать паттерн "слать каждый цикл, пока держишь"** для нового функционала, особенно
  для энкодера — иначе `ENC:+1` будет прилетать по несколько раз за 350 мс без реального
  поворота. Правильный паттерн: хранить предыдущее прочитанное состояние, слать только при
  изменении. Кнопки `STATS/ITEMS/DATA` можно не трогать (они и так работают), но для всего
  нового — делать по-другому
- **Декодирование A/B энкодера — через прерывания, не через опрос главного цикла.**
  Переходы на сигналах A/B (GPIO 5/6) при обычном прокруте пальцем идут на масштабе единиц
  миллисекунд — текущий период опроса 350 мс их физически не поймает. Нужно повесить
  `Pin.irq(trigger=Pin.IRQ_RISING | Pin.IRQ_FALLING)` на оба пина. В обработчике: прочитать
  оба пина → собрать 2-битное состояние → сравнить с предыдущим по таблице переходов →
  накапливать четверть-шаги; при накоплении ±4 (один полный механический "щелчок") — послать
  `ENC:+1` / `ENC:-1` и обнулить счётчик. Кнопка энкодера (SW, GPIO 7) может остаться в
  обычном цикле опроса вместе со STATS/ITEMS/DATA, но с паттерном "слать только при
  изменении" (см. пункт выше), не при каждом проходе
- **Радио-энкодер (GPIO 33/34/35, раздел 3.3) — тот же decode, что и у энкодера меню**,
  вынести в переиспользуемую функцию/класс вместо копипаста (два независимых экземпляра
  decode-состояния, разные обработчики `Pin.irq`). Дополнительно — локальный флаг `tuneMode`
  на ESP32, переключается по SW: в зависимости от флага исходящий шаг уходит как
  `RADIOTUNE:±N` либо `VOLUME:±N` (см. раздел 3.3), а не одно и то же имя команды всегда
- **Задействовать `on_rx`** — сейчас пришедшая с телефона строка просто ложится в
  `vars.sentVALUE` и всё. Нужно распарсить по конвенции из раздела 2 и реально дёрнуть
  нужную периферию (I2C-запись в RDA5807M, ШИМ на лампы и т.д.)
- Логика Гейгера (`WiFi.scanNetworks()` на сети `R10/R20/R50`) — отдельный код, не завязан
  на существующую BLE-часть, добавляется независимо, просто в конце цикла сканирования шлёт
  `GEIGER:<уровень>`

## 5. Что нужно добавить в приложение (`MainActivity.kt`)

- Расширить `when(menu)` в `menuChangeBLE()` (или, лучше, завести отдельный обработчик рядом,
  не раздувая одну функцию до бесконечности) — добавить ветки для новых входящих команд:
  `POWER:<0/1>`, `ENCBTN`, `ENC:...`, `GEIGER:...`, `HOLOTAPE:...`, `RADIOFREQ:...`,
  `RADIOPWR:<0/1>`, `RADIOTUNE:...`, `VOLUME:...`, `RADIOTUNEBTN`
- **`RADIOPWR:1`** (от ESP32, см. раздел 3.2) — переключить на экран радио. **`RADIOPWR:0`** —
  остаться на текущем экране, обновить только статус радио
- **`RADIOTUNE:±N`** — на экране радио сдвинуть частоту на шаг в соответствующую сторону,
  отправить `RADIOFREQ:<новое значение>` на ESP32. **`VOLUME:±N`** — изменить громкость
  воспроизведения. **`RADIOTUNEBTN`** — опционально показать индикатор текущего режима
  (тюнинг/громкость), если есть место на экране радио — не обязательно для базовой работы
- **Реализовать état-машину экрана согласно `POWER:<0/1>`** (см. раздел 3.1): `OFF` (чёрный
  экран) → получен `POWER:1` → анимация загрузки → `ON` (основной интерфейс) → получен
  `POWER:0` → анимация выключения → `OFF`. Применять состояние из ESP32 как есть, не
  тумблерить локально — телефон не хозяин состояния, только отражает то, что пришло
- Стартовое состояние приложения при холодном запуске — `OFF`, до первого `POWER:<state>`
  от ESP32 (см. раздел 3.1)
- Раз приложение должно реагировать на `POWER` даже когда его UI не на переднем плане —
  BLE-соединение обязано жить в **foreground service** с постоянным уведомлением, а не
  обрываться при сворачивании. Нужно: запрос исключения из battery optimization
  (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — иначе агрессивные вендоры вроде
  Xiaomi/Huawei убьют фоновую BLE-связь за минуты), на Android 13+ — рантайм-разрешение
  `POST_NOTIFICATIONS` для самого уведомления сервиса
- Парсинг `КЛЮЧ:ЗНАЧЕНИЕ` — простой `split(":")`, если ключ ожидает число — `toIntOrNull()`
  с проверкой на `null` (не доверять, что ESP32 всегда пришлёт валидную строку)
- Для команд телефон → ESP32 (`RADIOPWR`, `RADIOFREQ`, `HOLOTAPE:LIST/READ`) —
  использовать уже написанные `writeCharacteristic()`/`sendBLEText()`, они шлют произвольную
  строку, менять не нужно, просто вызывать с нужным текстом из новых экранов (Радио/Гейгер/Items)

## 6. Тестирование без железа (актуализация под вариант А)

Раньше в этом же разговоре обсуждали nRF Connect в общем режиме эмуляции периферии — теперь
это даже проще: у nRF Connect есть **готовый шаблон "UART"**, эмулирующий именно Nordic UART
Service из коробки, с теми же UUID. Не нужно вручную заводить кастомные характеристики —
подключаете PipDroid к телефону с nRF Connect в UART-режиме и руками из интерфейса шлёте
строки `GEIGER:140`, `RADIOFREQ:998` и т.д., проверяя, что новые ветки в `menuChangeBLE()`
(или отдельном обработчике) реагируют правильно — ещё до того, как прошивка на ESP32-S3
дойдёт до этих команд по-настоящему.
