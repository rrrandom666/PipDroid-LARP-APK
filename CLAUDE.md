# PipBoy LARP — контекст проекта для Claude Code

Этот файл — выжимка решений и контекста из большого обсуждения проекта вне Claude Code.
Полные документы (не дублируются здесь целиком, но стоит держать в проекте рядом):
`PipBoy_Roadmap.md` (общий roadmap) и `PipBoy_BLE_Protocol_v0.2.md` (протокол BLE).

**Разделение ответственности между файлами.** Статус разработки — что сделано, что в
работе, что следующее — всегда только в `PipBoy_Roadmap.md`, не здесь: два места для
одного и того же статуса неизбежно расходятся (так и случилось однажды — этот файл
отстал от Roadmap). Roadmap, раздел "2. Программная часть (PipDroid)" → "Этапы
разработки" — плоский нумерованный список: `✅` перед названием пункта — сделано, `👉` —
следующее в очереди, без пометки — просто ждёт своей очереди. Детальные чейнджлоги
отдельных крупных фич (конкретные баги, коммиты, находки по ходу реализации) — не внутри
самого списка этапов, а отдельными `###`-подразделами того же раздела 2 (например
"Анимация включения и выключения" рядом с моделью навигации энкодером). CLAUDE.md — про
то, что стоит помнить между сессиями и что не является статусом: архитектурные решения,
протокол, нетривиальные находки и грабли, которые иначе придётся переоткрывать заново.

**Целевое видение приложения PipDroid** (три режима работы — телефон/PipBoy 2000/PipBoy
3000, локализация, перестройка ITEMS/DATA, реальные радио и карта, голодиски, журнал,
часы с таймером, анимация POWER) зафиксировано в `PipBoy_Roadmap.md`, раздел "Видение
приложения — финальная точка". Счётчик радиации в STATS — не конфликтует с отдельным
проектом «Игровая радиация», это две разные вещи, см. раздел "Периферия" ниже.

## Что это за проект

Функциональный Pip-Boy для полигонных ролевых игр по вселенной Fallout (реалистичный LARP —
игроки реально делают то, что должен делать персонаж). Корпус — 3D-печатная модель Vault901
"Pip-Boy 2000 Mk VI". Софт — форк приложения **PipDroid**
(https://github.com/Malto4/PipDroid-APK, автор Malto4).

**Статус разрешения от автора PipDroid:** написано автору (Reddit + GitHub issue) с просьбой
разрешить форк под некоммерческий LARP-проект, ответа больше двух недель нет. Отправлено
уведомление, что разработка началась локально (без публикации/раздачи), пока ждём ответа.
В репозитории нет файла LICENSE — только фраза в README про некоммерческое фанатское
использование ("Wasteland reenactments" там же упомянуты явно, это ровно наш случай).
**Не публиковать и не раздавать APK игрокам до явного ответа автора.**

**Отдельно — визуальная дистанция от официального приложения Bethesda**
(`com.bethsoft.falloutcompanionapp`). Иногда используем его как референс структуры/логики
экранов (см. roadmap — мастер PipBoy 2000/3000, новая шапка) — это нормально, но не значит
"копировать дословно". Декоративные детали (конкретные иконки, скобки-декорации у активной
вкладки, шрифт/раскладка) — не переносить один в один. Это отдельный риск от разрешения
автора PipDroid выше: некоммерческий фанатский статус форка не должен размываться
visually-too-close клоном продукта другого правообладателя.

## Ключевое архитектурное решение: BYOD

Ядро системы — **личный телефон игрока**, а не выделенный донор-девайс. Легко вставляется/
вынимается из корпуса. Следствия:
- GPS и микрофон — от телефона, отдельные модули не нужны
- Крепление в корпусе — универсальное/регулируемое (зажимы, вставки), не подгонка под одну
  модель. Оригинальные Phone Support Bar / Display Case из STL рассчитаны на телефоны ~2018
  года (Display Case ~110×106×48мм) — малы для современных, нужна доработка
- Пейринг по BLE — у каждого экземпляра PipBoy своё BLE-имя, игрок сам подключает свой телефон
- Разъём зарядки телефона в корпусе — под вопросом, вероятно не нужен при BYOD
- Для разработки нужен **отдельный физический Android-телефон** (эмулятор не умеет BLE)

## Периферия

**ESP32-S3-DevKitC-1 (модуль WROOM-1)** — полноразмерная плата с полной распиновкой, выбрана
сознательно вместо легаси-платы форкнутого проекта (папка `ESP32_S3_Mini_PythonFiles` —
просто унаследованное название, к плате отношения не имеет). Причина выбора и финальная
карта GPIO — в `PipBoy_BLE_Protocol_v0.2.md`, раздел 4.0. Три роли в одном МК:
1. BLE-мост к телефону
2. Сканер Wi-Fi для Гейгера
3. USB Host для чтения голодиска (bare-флешка на 4 магнитных pogo-контактах, не активное
   устройство — геркон/неодимовый магнит из старого дизайна больше не используются)

Риск: Wi-Fi scan может мешать BLE (общий радиотракт). План Б (не закупать заранее) — отдельный
ESP8266 только под Wi-Fi-сканирование, к ESP32-S3 по UART.

**Питание корпуса — автономное, отдельная схема от телефона** (roadmap, Phase C): LiPo (1S,
3.7В) → TP4056 с защитой → свой boost-преобразователь 3.7В→5В → 5V/VIN платы ESP32-S3
(тот же вход, что у USB). Тумблер питания — в разрыв между бустом и платой, не на цепи
заряда (заряжать можно при выключенном питании). Порт зарядки — свой у модуля TP4056
(USB-C/micro-USB), выведен наружу корпуса; USB-C самой платы ESP32-S3 остаётся внутренним,
только для прошивки. **Кнопка POWER из протокола — логический тумблер состояния
(`PipBoy_BLE_Protocol_v0.2.md`, раздел 3.1), не реальное включение электропитания** — ESP32
должен уже быть физически запитан и вещать BLE до того, как POWER что-либо переключает (это
же условие для пейринга — корпус должен быть включён питанием заранее). Ёмкость и физическое
место аккумулятора — под вопросом, зависит от свободного объёма в конкретной 3D-модели,
см. открытые вопросы.

**Гейгер на ESP32 (прошивка PipBoy)** — только мгновенное чтение, сканирует сети
`R10/R20/R50/R100`. Уровень радиации — **фиксированная доза по имени маячка, не по силе
сигнала** (пересмотрено на этапе 22, было наоборот изначально, см. `PipBoy_Roadmap.md`,
"Счётчик радиации — пересмотр механики Гейгера"): `R10` = 5 рад/сек, `R20` = 10, `R50` = 25,
`R100` = 50 (смертельная доза 1000 рад за 20 сек). Видно несколько маячков сразу — действует
тот, что даёт максимальную дозу. Стрелка вольтметра и частота треска пьезодинамика — от
текущей дозы; нет ни одного маячка — тишина/ноль. Без памяти, без накопления дозы, без
сброса на уровне самого сканера — это не меняется, ESP32 остаётся тупым мгновенным
датчиком, накопление — целиком на стороне приложения (см. ниже). Индикация — аналоговый
вольтметр (ШИМ+RC-фильтр с ESP32-S3), не степпер (степпер — только если делать отдельный
физический циферблат часов).

**Официальный датчик радиации игрока (отдельный проект «Игровая радиация») — НЕ часть
PipBoy.** Отдельное носимое устройство на игроке (ESP8266 + LED), сканирует те же сети,
копит дозу и обнуляется **только мастерами через сеть-сброс** `R0`/`RAD0` (в исходном
документе название сети противоречиво, не уточнено). Это авторитетный источник дозы для
игровых правил — PipBoy на него никак не влияет и не может обнулить.

**Счётчик радиации на ITEMS/Гейгер (приложение PipDroid) — отдельная, дополнительная
фича, не конфликтует с официальным датчиком.** Реализовано на этапе 22. Это удобство для
игрока: приложение суммирует дозу по `GEIGER:<рад/сек>` от ESP32 (шлётся раз в секунду
безусловно, накопление — на стороне приложения, не прошивки), клампит на [0, 1000] и
показывает на шкале со стрелкой (0-1000 рад) и **обнуляется самим игроком кнопкой на
экране**, когда захочет. Переживает перезапуск приложения (`SharedPreferences`). Не
авторитетный источник для игровых правил — просто личный трекер поверх Гейгера,
параллельно официальному датчику, а не вместо него.

## Протокол связи телефон ↔ ESP32-S3

**Вариант А** (принят после находки существующего кода): не кастомный GATT-сервис, а
расширение уже готовой архитектуры автора PipDroid — **Nordic UART Service (NUS)**.

- Service UUID `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`, TX `...0003` (ESP32→телефон, notify),
  RX `...0002` (телефон→ESP32, write)
- Обмен — plain text команды, конвенция `КЛЮЧ:ЗНАЧЕНИЕ` для параметризованных, просто
  ключевое слово для остальных (как уже есть `STATS`/`ITEMS`/`DATA`)
- Уже работает в коде: 3 кнопки (GPIO 16/17/18, active-low, pull-up) на ESP32-S3
  (`ESP32_S3_Mini_PythonFiles/main.py`, класс `BLESimplePeripheral` определён прямо в файле,
  `ble_uart_peripheral.py` — НЕ используется, мёртвый референсный файл), опрос раз в 350мс,
  шлёт строку **каждый цикл, пока кнопка держится** (не событие изменения)
- На телефоне: `MainActivity.kt`, `menuChangeBLE()` — `when(menu){"STATS"->...}`.
  `BluetoothGattCallback.onCharacteristicChanged` уже работает
- Пейринг — выбор из списка найденных сканом устройств (ручной ввод MAC и UUID убран вместе
  с редизайном Settings). Сохраняется только MAC (`bluetoothMAC`); UUID сервиса и характеристик
  берутся из дефолтов NUS, ключи `bluetoothSUUID`/`bluetoothRUUID`/`bluetoothWUUID` читает сам
  `PipBoyBleService` и никто их не пишет
- Путь телефон→ESP32 (`writeCharacteristic()`/`BluetoothController.send()`) привязан к смене
  частоты радио: `RADIOFREQ:<val>`, и `on_rx` в прошивке её разбирает. Это единственная команда
  в эту сторону — имена разделов приложение слать перестало (см. ниже). На живом ESP32 путь не
  проверялся ни разу, железа нет

**Новые команды (см. полный список в `PipBoy_BLE_Protocol_v0.2.md`):**
`POWER`, `ENCBTN`, `ENC:±N`, `GEIGER:<рад/сек>`, `HOLOTAPE:1/0`, `RADIOFREQ:<val>` (ESP32→телефон);
`RADIOPWR:1/0`, `RADIOFREQ:<val>`, `HOLOTAPE:LIST`, `HOLOTAPE:READ:<n>`
(телефон→ESP32). Голодиск-чанкинг (`HOLOTAPE:DATA:...`) — черновой, ждёт теста throughput.
Список неполный и устаревает по ходу работы — актуальный источник истины по командам и
GPIO всегда `PipBoy_BLE_Protocol_v0.2.md`, этот файл только даёт общую картину.

**Что нужно поправить в прошивке при добавлении новых команд:**
- Назначить GPIO под Power/энкодер (свободные, избегать 0/3/45/46 — strapping-пины, и 19/20 —
  USB D+/D-, если ESP32-S3 держит нативный USB Host для голодиска)
- Для нового функционала — слать **по изменению состояния**, не по опросу каждые 350мс
  (иначе `ENC:+1` будет дублироваться). Существующие STATS/ITEMS/DATA не трогать, они рабочие
- `on_rx` уже разбирает `КЛЮЧ:ЗНАЧЕНИЕ` и дёргает периферию (`RADIOPWR` → `radio_power()`,
  `RADIOFREQ` → `radio_set_frequency()`). Ветки под имена разделов там нет и не нужно —
  приложение их не шлёт

## Архитектурный принцип: тематизация интерфейса

**Любой новый или дорабатываемый экран должен краситься текущей темой оформления**
(Green/Amber/White/Blue, `playerUIColour_SPKey` в SharedPreferences) — кнопки, иконки,
заголовки, основной текст и прочие подходящие элементы, а не жёстко зашитым цветом одной
темы. Это не опция, а прямое следствие того, что тема вообще существует как фича приложения.

Установлено на примере кнопок/текстов экрана выбора режима и мастера PipBoy 2000/3000
(roadmap, косметические правки): изначально были жёстко зелёными, поправлено на тематизацию.

**Как это устроено в коде** (`MainActivity.kt`):
- Активность применяет **единственный раз** при старте (`onCreate`, `theme.applyStyle(...)`)
  один из `Theme.PipDroid.{Green,Amber,White,Blue}UI` — тема на лету **не переприменяется**,
  activity не пересоздаётся при смене цвета в Settings
- Поэтому все элементы, которые должны краситься динамически (в т.ч. при живой смене темы в
  Settings), красятся **не через саму Activity-тему**, а вручную кодом, читая
  `sharedPreferences.getInt(playerUIColour_SPKey, 0)` — есть 2 параллельных, оба рабочих пути:
  - Уже существовавший до правок: `applyAppTheme()`/`applyBackgroundResource()`/
    `applyTextColor()`/`applyProgressDrawable()` — точечные списки конкретных View
  - Добавлен в этой правке: `currentWizardAccentColor()` — короткий helper, возвращает
    `themeGreen`/`themeAmber`/`themeWhite`/`themeBlue` по индексу; кнопки красятся через
    `button.backgroundTintList = ColorStateList.valueOf(accent)` поверх **нейтральных**
    (белых/прозрачных) drawable-заготовок, тексты — через `setTextColor(accent)`
- Готовое исключение, ничего не делать: **`ImageView.tint`** уже подхватывает тему сам —
  `Theme.PipDroid.{Green,Amber,White,Blue}UI` определяет `android:tint`, и ImageView без
  явного своего tint наследует его через дефолтный стиль. Проверено на иконке Vault-Boy в
  мастере (`pipboy_3nv.png`, обычный статичный PNG без своей логики) — уже была тематизирована
- **backgroundTintList на кнопках исторически был источником бага** (AppCompat сам тянул
  тон от `colorPrimary` темы поверх кастомного drawable, см. историю правок кнопок) — теперь
  это осознанно используемый, а не побочный механизм, но `android:backgroundTint="@null"`
  в стиле/XML не работает на этом AGP/AAPT2 (см. окружение разработки ниже), тон снимается/
  ставится только кодом
- **Тот же эффект — не только у кнопок.** Найдено на карте (roadmap, этап 18): обычный
  `TextView.setBackgroundColor(...)` из кода реально красился в акцент темы, а не в
  переданный цвет — AppCompat подмешивает `backgroundTint` поверх программно выставленного
  фона у любого View, не только у кнопок со своим drawable. Если код красит
  фон/текст, а на экране виден другой цвет (обычно — акцент текущей темы) — сначала
  подозревать этот механизм, чинить через явный `view.backgroundTintList = null` перед
  `setBackgroundColor()`/`setBackgroundResource()`, а не искать баг в своей логике

## Ещё находки про вёрстку/ввод (roadmap, этап 18 — карта; этап 27 — энкодер)

- **Стили с `android:layout_height="0.0dip"`** (`SettingsButtonStyle`, `PipWizardButtonStyle`,
  `CNDEFFRADButtonStyle` — у всех трёх высота задана в самом стиле как `match_constraint`)
  **требуют явного `android:layout_height` на конкретном инстансе View**, если та не имеет
  пары top+bottom constraint. Без этого высота повисает неопределённой, и View схлопывается
  в невидимую — причём не только визуально: тапы в её области проваливаются на то, что под
  ней. Все рабочие примеры в проекте (Settings, Bluetooth) всегда прописывают
  `layout_height` явно рядом со `style=` — держаться того же правила у любого нового поля с
  одним из этих трёх стилей.
- **Программный вызов клавиатуры (`InputMethodManager.showSoftInput()`) вне прямого ответа
  на тач Android часто просто игнорирует.** В проекте нет ни одного места, где клавиатура
  вызывалась бы кодом — Settings/Filter (единственные экраны с `EditText`) полагаются на
  обычный тап по полю, системным поведением. Это и есть рабочий паттерн; не пытаться
  форсировать `requestFocus()`/`showSoftInput()` вручную при открытии панели с полем ввода.
- **Прицел-уголок энкодера (`focus_corner_brackets`, отдельный `View` с отрицательным
  margin поверх кнопки, см. `viewGeigerResetFocus` и т.п.) работает, только если он —
  ПРЯМОЙ ребёнок того же `ConstraintLayout`, что и кнопка, на которую он ссылается через
  `app:layout_constraintXxx_toXxxOf="@id/..."`.** `ConstraintLayout` резолвит такие ссылки
  только среди своих непосредственных детей — если кнопка на самом деле лежит на уровень
  глубже (например, внутри `LinearLayout`, добавленного ради `measureWithLargestChild` или
  весов), прицел молча схлопывается в (0,0) и не виден, хотя `visibility` в коде выставляется
  правильно (найдено на Cancel/Save в редакторе Journal, roadmap, этап 27 — у соседней Mic-
  кнопки, лежавшей прямо в `ConstraintLayout`, тот же приём работал). Чинится не поиском бага
  в логике `setFocusBracketsVisible()`/коде, а переносом кнопки-цели на тот же уровень
  вложенности, что и её прицел — ценой любых удобств вложенного `LinearLayout`
  (`measureWithLargestChild` и т.п.), которые придётся пересобирать через сами constraints.

**Полноэкранный слой сам по себе не перехватывает тач.** View поверх интерфейса пропускает
касания на то, что под ним, пока у него нет `android:clickable="true"`. Наступали дважды: у
мастера PipBoy 2000/3000 (там починили иначе — гасили кнопки шапки и футера, потому что у
самого мастера есть свои кликабельные элементы) и у слоя анимации включения/выключения плюс
чёрного экрана OFF — тапы во время заставки переключали вкладки и жали кнопки под ней. У
слоёв без собственных кнопок правильное лечение — `clickable`/`focusable` на корне. Сознательное
исключение: оверлей глитча (`iv_glitch_overlay`) тач НЕ поглощает — он вспыхивает на 60-150мс
поверх рабочего экрана, и касание в этот момент должно доходить до интерфейса под ним.

**Затенённый элемент обязан отвечать звуком ошибки, а не молчать.** Конвенция проекта:
недоступность — это только визуальное затенение (`alpha`), тап всё равно доезжает до
обработчика, и тот играет `playErrorAudio()`. Так устроены пункты бокового меню
(`SidebarMenuItem.enabled` — исключительно тон, исход решает сам экран) и голосовые команды.
Грабли: `View.isEnabled = false` выглядит естественным способом «выключить кнопку», но он
глотает касание целиком — обработчик не вызывается, и играть звук становится физически негде,
элемент молчит. Именно так молчала [Пауза] на экране Таймера при активном таймере ранения.
Не выключать кнопку через `isEnabled`, если у неё есть запрещённое состояние: держать флаг
разрешения рядом и проверять его в общем теле обработчика.

**Гейт по режиму работы разбросан по четырём независимым путям, и два из них забываются.**
Списки, зависящие от `pipBoyMode` (боковые меню, кнопки «назад»), пересобирает
`refreshSidebarBackItems()`. Остальные три ловились по одному, каждый — прогоном на устройстве:

- **Строка 2** строится **только** из `menuChangeBLE()` → `menuOptionClickedBLE()` →
  `setupRow2()`, и при смене режима её никто не трогал — она оставалась от прежнего режима,
  разъезжаясь с деревом на один индекс (GEIGER скрыт в Телефоне, поэтому размеры списков
  разные). Симптом обманчивый: подсветка встаёт не на тот пункт, а последний становится
  недостижим, хотя вычисление индексов корректно с обеих сторон
- **Стек уровней энкодера.** Само дерево (`itemsMenuRoot()` и соседи) действительно
  пересчитывается на каждом обращении — но `MenuNavigator.Level` **захватывает** список узлов
  в момент провала в уровень, а `childrenProvider` дёргается только при спуске. Пока курсор
  стоит внутри уровня, его состав заморожен прежним режимом: пункт «В меню» виден в боковом
  списке, но энкодер до него не достаёт, а после подъёма корень раздела оказывается на узел
  короче строки 2. Чинит `menuNavigator.rebuildLevels()`, и она обязана идти **до** пересборки
  строки 2 — та читает `rootCursor()`. Курсор восстанавливается по id узла, а не по индексу:
  GEIGER встаёт первым пунктом корня ITEMS и сдвигает все остальные разделы
- Оба симптома маскируются обычными действиями и потому выглядят «плавающими»: создание записи
  зовёт `replaceChildrenOf()` и чинит уровень, переход в соседний раздел и обратно зовёт
  `resetToRoot()` и чинит корень. Баг «уходит сам» — но только до следующей смены режима

Правило: любая новая сущность, гейтящаяся режимом, обязана попасть в
`refreshSidebarBackItems()` — это единственная точка «режим стал известен/сменился». Осторожно
с пустой строкой 2: её первую сборку держит гейт `row2Views.isEmpty()` в `onBootFinished`, и
безусловная пересборка сломала бы стартовую последовательность.

**`android:overScrollMode="never"` на списке убивает полосу прокрутки.** Найдено на
SPECIAL/Skills (этап 30): список прокручивался, `computeVerticalScrollRange` был больше
`extent`, полоса включена, thumb выставлен, геометрия совпадала с работающими экранами до
пикселя — а полосы не было. Единственным отличием от рабочих Perks/Мелодий оказался этот
атрибут; после его удаления полоса появилась. Точного места в исходниках фреймворка, где
одно влияет на другое, я не проследил — но корреляция была без единого контрпримера, и
атрибут отключает только свечение при перетягивании за край, то есть спискам не нужен.
Не ставить его на то, у чего должна быть полоса.

## Сверка слепков — страховка при рефакторинге

`dev-tools/refactor_snapshot.sh <метка>` собирает приложение и снимает слепок:
байткод (`javap -p -c` по всем классам), его нормализованную копию (замаскированы
константы — удаление ресурса перенумеровывает id, а те инлайнятся в байткод), список
объявленных членов классов, файлы и имена ресурсов, динамические имена.
`... diff <a> <b>` сверяет два слепка. Смысл: шаг, который не должен менять поведение
(чистка комментариев, удаление мёртвого кода), обязан дать совпадение — компилятор этого
не проверяет. Для удалений точнее всего `members.txt`: при удалении кода смещения в
байткоде плывут по всему методу, а список членов меняется ровно на то, что убрали.

**Для выноса экрана в контроллер слепок бесполезен — методы меняют класс, байткод
расходится весь.** Там свои два инструмента, оба в `dev-tools/`:
- `controller_boundary_measure.py --pattern '<слова экрана>'` — ДО выноса: где граница
  проходит на самом деле. Считает членов экрана, поля состояния и, главное, обращения
  к ним извне **без** `onCreate` (тот уезжает вместе с блоком, его обращения в поверхность
  не входят). Решение принимается по этому числу, а не по ощущению «кусок выглядит
  отдельным»: у Часов узкий вынос отменил именно замер, у голоса — отменил вынос целиком.
  Шаблон по именам врёт в обе стороны, список членов обязателен к просмотру глазами.
  **Перемерять перед началом работы, а не верить числу, записанному в очередь**: оценка
  голоса («~190 строк») протухла ровно тем, что в неё молча входил лаунчер, который никуда
  не едет. Замер — минута, вынос — сессия
- **Размер — не единственный критерий, и не главный.** Bluetooth (190 строк) выносить стоило
  за развязку: сканер перестал ходить через активность. Голос (98 строк за вычетом диспетчера
  и лаунчера) выносить не стоило ровно потому, что развязка у него отрицательная — `voice/`
  уже отдаётся в `MapController`/`JournalController` напрямую, и контроллер стал бы лишним
  хопом. Прежде чем резать, спросить: какая связь после выноса исчезнет, а какая появится
- `controller_extract_check.py --range A-B --rename СТАРОЕ=НОВОЕ` — ПОСЛЕ выноса: сверяет
  строки исходных диапазонов из `git show HEAD` с новым файлом в обе стороны, применив
  механические переименования. Смысл не в нулевом выводе, а в том, чтобы КАЖДОЕ
  расхождение было заявленным (подстановка колбэка, `this`→`activity`, `private`→`fun`).
  Незаявленное расхождение — потерянная или придуманная строка

**Чего не ловит ни один из двух, и что решается до вызова инструментов.** Оба сверяют текст, а
не смысл, поэтому две вещи остаются на голову:

- **Помощник с «чужим» потребителем уезжает молча.** Функция, названная по экрану, вполне может
  краситься где-то ещё: `setWizardButtonState()` красит и кнопки тьюториала, `equalizeButtonWidths()`
  — их же. Замер по именам такое относит к экрану, сверка выноса не возражает (строка честно
  переехала), ловит только компилятор — и только пока функция `private` в том же файле. Правило
  до выноса: у каждого помощника проверить грепом список вызовов, и если хоть один вне
  выносимого экрана — помощник остаётся в активности и прокидывается колбэком
- **Разбросанный по `onCreate` экран: единственный `setup()` двигает его блоки.** Код экрана
  редко лежит в `onCreate` одним куском — у STATS он был пятью, вперемешку с чужими. Один
  `setup()` (как у Карты, Часов, Журнала) неизбежно переставляет часть блоков, а сверка выноса
  этого не видит вовсе: строки на месте, изменился только порядок исполнения. Плодить по
  `setup*()` на блок ради буквальности — хуже, поверхность контроллера раздувается вдвое.
  Правило: ставить единственный вызов на место **первого** блока, чтобы остальные ехали **вверх**
  — тогда к прежней точке всё, что там существовало, существует и теперь, и остаётся проверить
  ровно две вещи по каждому блоку: не читает ли код между ними перенесённого состояния и не
  зависит ли перенесённый блок от того, что стоит между. Регистрация слушателей и тонировка
  переезжают свободно, опасны только исполняемые присваивания и сборка адаптеров
- **Слияние двух похожих операций в одну «семейную» — тихое расширение поведения.** Соблазн:
  мастер и экран выбора режима — одно семейство, пусть `hide()` гасит оба. Но у объединённого
  метода появляются места вызова, где вторая вьюха реально видима, и там поведение меняется
  (`applyPowerState()` по приходу `POWER` погасил бы мод-селект, открытый через Settings). Сверка
  этого не видит: строк не потеряно, они просто теперь исполняются чаще. Проверять по каждому
  месту вызова отдельно, а не по тому, «одно ли это семейство экранов»

**`registerForActivityResult` остаётся в активности, и это ломает вывод типов у контроллера.**
Лаунчеры регистрируются до `onStart`, поэтому все четыре живут полями `MainActivity`, а
контроллеру нужное действие прокидывается колбэком (`requestEnableBluetooth`). Но если колбэк
лаунчера в ответ зовёт метод контроллера, ссылки замыкаются в кольцо, и `kotlinc` падает с
`Type checking has run into a recursive problem` на строке лаунчера — хотя ошибка не в нём.
Лечится явным типом на одной из двух сторон: `private val bluetooth: BluetoothController by lazy`.
Пара «лаунчер ↔ контроллер» есть и у голоса (`openVoiceModelZipLauncher`), то же ждёт и там.

**Правило комментариев в этом проекте:** одно предложение, объявляющее функциональный блок
(«делаем X»). Не пересказ кода построчно, не история находок, не ссылки на этапы roadmap —
всё это живёт в `PipBoy_Roadmap.md`. Проверено, что комментарии не влияют на байткод: их
правка обязана давать побайтно идентичный слепок.

**Чего компилятор не видит и что ломается молча** (проверять греп-поиском после любой
правки, слепок ловит только часть):
- `getIdentifier` по имени ресурса — `perk_<id>_name`/`perk_<id>_desc` (277 строк
  `strings.xml` выглядят «неиспользуемыми» для любого статического анализа, включая
  `lint`/`UnusedResources` — вслепую его здесь применять нельзя)
- ключи SharedPreferences: 8 объявлены константами `*_SPKey` в активности, ещё четыре — в
  контроллерах (`selectedRingtone_SPKey` в `ClockController`, `selectedPerks_SPKey` в
  `StatsController`, `bluetoothMAC_SPKey`/`bluetoothSUUID_SPKey` в `BluetoothController`),
  но **8 по-прежнему живут голыми строковыми литералами**
  (`appLanguage`, `ShowTutorial`, `TrueFullscreen`, `AmbientSoundEnabled`, `width`,
  `height`, `leftMargin`, `topMargin`) — опечатка при переносе стирает сохранёнки игрока
- текстовые команды BLE — контракт с прошивкой ESP32
- порядок вызовов внутри `onCreate` — перестановку блоков компилятор разрешит

**А что компилятор видит — прогонять как отдельный чек-лист: сборка держится без единого
варнинга.** Греп по *именам объявлений* (чем волна 1 искала мёртвый код) не видит
неиспользуемые **локальные** переменные внутри живых функций, а `kotlinc` видит — и через
них вытягивается настоящий мёртвый код (две функции нашлись именно так). Плюс варнинг про
nullability — не всегда косметика: `Unnecessary safe call` рядом с `!!` обычно значит, что
`?.` и `!!` перепутаны местами и прикрывающий `?:` относится не к тому операнду (латентный
NPE в `onFling`). Смотреть строки `w:` в выводе `./gradlew assembleDebug`, а не только
`BUILD SUCCESSFUL`; ненулевой счётчик варнингов — регрессия.

**Зелёный тест с первого прогона ничего не доказывает — проверять мутацией.** Внести поломку
в продакшен, убедиться, что тест упал, вернуть файл. На тестах `MenuNavigator` это сразу
поймало слепой тест: инвариант «курсор родителя сохранился» проверялся на курсоре, стоящем
на нуле, а мутация «сбросить курсор на 0» даёт тот же ноль — сохранение и сброс неотличимы.
Отсюда правило: **инвариант «значение сохранилось» нельзя проверять на значении по
умолчанию.** Возвращать файл после мутации копией (`cp` из `/tmp`), а не `git checkout` —
тот сносит заодно и всю несохранённую работу в этом файле.

**Слепая зона обоих способов сразу — неиспользуемые импорты.** Импорт не объявление, поэтому
греп по именам объявлений его не ищет; `kotlinc` про него не предупреждает вообще (это
инспекция IDE, а не варнинг компилятора), поэтому и чек-лист варнингов пуст. Так 18 мёртвых
импортов пережили обе волны уборки и нашлись только при выносе Карты. Проверять отдельным
проходом: для каждого `import a.b.C` — есть ли `C` в теле файла. Правка безопасна по
построению: слепок обязан быть идентичен побайтно, импорты не порождают байткода.

## Локализация — заметки

Статус (что переведено, что осознанно нет, открытые находки про STATS/Perks) — в
`PipBoy_Roadmap.md`. Здесь — только то, что не завязано на текущий статус и пригодится
при следующей правке локализации/языка.

**CSV теряет пробелы по краям значений.** Таблица переводов — `localization/
strings_ru.csv`, редактируется пользователем в IDE. Табличные редакторы (Excel/Numbers)
обрезают пробелы по краям значений при круге через CSV — если у строки есть смысловые
пробелы в начале/конце (напр. `" - Level "`), после копирования в `values-ru/strings.xml`
их приходится восстанавливать руками и оборачивать в `"..."` (Android и сам обрежет
пробелы в теле `<string>`, если не взять значение в кавычки — вторая, отдельная причина
той же обрезки).

**Скрипт сверки CSV ↔ ресурсов существует.** Сравнивает `source_text` из
`localization/strings_ru.csv` с фактическим значением в `values/strings.xml` (с поправкой
на разницу экранирования `\n`/`…`/апострофов между CSV и Android-синтаксисом) — находил
строки, где после правки `values/strings.xml` остался русский текст без английской
версии. Использовать перед тем как считать очередной раунд перевода завершённым, не
полагаться на память о том, что уже поймано вручную.

**Реальный список Perks живёт не в `strings.xml`, а в `Data.kt`** (`val perks =
listOf(...)`, ~130 перков, имя+описание на каждый — лор Fallout NV: V.A.T.S., компаньоны
Бун/Кэсс/Вероника/Рауль/ED-E/Рекс, наркотики). Экран строится программно
(`StatsController.setupStatsPerks()` поверх общего `SidebarMenuAdapter`) из `Data.kt`, не из
XML. Семь строк `stats_perks_perk1-7` в `strings.xml` — мёртвый код (переведены до этой
находки, `layout_tab_stats_perks.xml`, где они использовались, нигде не показывается —
`visibility` всегда `GONE`).

**В `Data.kt` кроме перков лежит `ringtoneTracks`** (`RingtoneTrack`, мелодии будильника) —
это живой список, из него `ClockController` строит раздел Часы/Мелодия. Больше в файле нет
ничего: `val dmiscs` (5 фейковых записей fruit/nut/bird) убран ещё волной 1.

**Язык интерфейса — через `MainActivity.attachBaseContext()`, не
`AppCompatDelegate.setApplicationLocales()`** — для последнего нужен AppCompat 1.6.0+, а в
проекте 1.3.1, апгрейдить не стали (риск сломать плотно закреплённый по версиям тулчейн,
см. окружение разработки ниже). Если язык не выбран явно (`appLanguage_SPKey`), контекст
не подменяется вообще и языком продолжает рулить система через обычный `values-ru`
фолбэк; если выбран — подменяется `Locale` через `createConfigurationContext()`.
`Configuration` в этом методе — `android.content.res`, не `org.osmdroid.config.Configuration`
(тот уже импортирован под тем же именем в файле, поэтому FQCN вместо второго import).

**Баг: статус Bluetooth показывал внутренний токен вместо текста.**
`updateBLEConnected()` выставлял отображаемый текст напрямую из `status: String`
(внутреннего токена состояния, сравнивается через `==`) — исправлено, `status` теперь
только для сравнения, текст берётся из `R.string.bluetooth_status_connected`/
`_disconnected`. Общий урок: если у View есть и токен-состояние, и отображаемый текст —
не путать эти две роли в одной переменной.

**Баг: мастер PipBoy 2000/3000 прерывался экраном Settings.** Вызванный через
Settings → "Изменить" режим работы, мастер не открывался сразу — `selectPipBoyMode()`
прятал только экран выбора режима, а сам Settings (из-под которого он был открыт)
оставался видимым под ним и выходил на передний план после закрытия мод-селекта, вместо
первого шага мастера. Исправлено: `selectPipBoyMode()` дополнительно закрывает Settings
(если он был открыт) тем же путём, что и его штатный крестик. Общий урок: если экран A
может быть открыт поверх экрана B, а логика A показывает экран C — проверить, что B тоже
закрывается, а не просто перекрывается.

## BOM (актуальная смета)

Итог по фиксированным позициям — **≈4000 ₽** на один экземпляр PipBoy (без 3D-печати корпуса,
без резервных/опциональных позиций, без разъёма зарядки телефона — под вопросом при BYOD).
Включает автономное питание корпуса (аккумулятор, заряд/защита, свой boost, тумблер — см.
раздел «Периферия» выше). Телефон в BOM не входит (BYOD). Полная таблица — в `PipBoy_Roadmap.md`.

## Открытые вопросы

- Название сети-сброса для датчика дозы игрока: `R0` (по коду) vs `RAD0` (по тексту исходного
  документа) — противоречие не разрешено, датчик игрока всё равно отдельный проект
- Скан маячков Гейгера на ESP32 остаётся раз в 6 сек (блокирующий `WLAN.scan()`) — при
  смертельной дозе `R100` за 20 сек это до трети времени на устаревших показаниях при
  входе/выходе из зоны. Осознанно отложено до появления реального железа
- Нужен ли вообще pogo-pin разъём зарядки в корпусе при BYOD
- Сколько игроков одновременно на площадке — не зафиксировано, важно для смет отдельного
  проекта «Игровая радиация» (не для этого репозитория)
- **Ёмкость и физическое место LiPo-аккумулятора питания корпуса** — не определены, зависят
  от свободного объёма в конкретной 3D-модели после размещения платы ESP32-S3/FM-модуля/
  пого-контактов/телефона. Вероятный кандидат по месту — Cuff 1 (roadmap, раздел 5), но не
  обмерян под это отдельно
