# PipBoy LARP — контекст проекта для Claude Code

Этот файл — выжимка решений и контекста из большого обсуждения проекта вне Claude Code.
Полные документы (не дублируются здесь целиком, но стоит держать в проекте рядом):
`PipBoy_Roadmap.md` (общий roadmap) и `PipBoy_BLE_Protocol_v0.2.md` (протокол BLE).

**Целевое видение приложения PipDroid** (три режима работы — телефон/PipBoy 2000/PipBoy
3000, локализация, перестройка ITEMS/DATA, реальные радио и карта, голодиски, журнал,
часы с таймером, анимация POWER) зафиксировано в `PipBoy_Roadmap.md`, раздел "Видение
приложения — финальная точка". Счётчик радиации в STATS — не конфликтует с отдельным
проектом «Игровая радиация», это две разные вещи, см. раздел "Периферия" ниже.

## Что это за проект

Функциональный Pip-Boy для полигонных ролевых игр по вселенной Fallout (реалистичный LARP —
игроки реально делают то, что должен делать персонаж). Корпус — 3D-печатная модель Vault901
"Pip-Boy 2000 Mk VI". Софт — форк приложения **PipDroid**
(https://github.com/Malto4/PipDroid-APK, автор Malto4).

**Статус разрешения от автора PipDroid:** написано автору (Reddit + GitHub issue) с просьбой
разрешить форк под некоммерческий LARP-проект, ответа больше двух недель нет. Отправлено
уведомление, что разработка началась локально (без публикации/раздачи), пока ждём ответа.
В репозитории нет файла LICENSE — только фраза в README про некоммерческое фанатское
использование ("Wasteland reenactments" там же упомянуты явно, это ровно наш случай).
**Не публиковать и не раздавать APK игрокам до явного ответа автора.**

**Отдельно — визуальная дистанция от официального приложения Bethesda**
(`com.bethsoft.falloutcompanionapp`). Иногда используем его как референс структуры/логики
экранов (см. roadmap — мастер PipBoy 2000/3000, новая шапка) — это нормально, но не значит
"копировать дословно". Декоративные детали (конкретные иконки, скобки-декорации у активной
вкладки, шрифт/раскладка) — не переносить один в один. Это отдельный риск от разрешения
автора PipDroid выше: некоммерческий фанатский статус форка не должен размываться
visually-too-close клоном продукта другого правообладателя.

## Ключевое архитектурное решение: BYOD

Ядро системы — **личный телефон игрока**, а не выделенный донор-девайс. Легко вставляется/
вынимается из корпуса. Следствия:
- GPS и микрофон — от телефона, отдельные модули не нужны
- Крепление в корпусе — универсальное/регулируемое (зажимы, вставки), не подгонка под одну
  модель. Оригинальные Phone Support Bar / Display Case из STL рассчитаны на телефоны ~2018
  года (Display Case ~110×106×48мм) — малы для современных, нужна доработка
- Пейринг по BLE — у каждого экземпляра PipBoy своё BLE-имя, игрок сам подключает свой телефон
- Разъём зарядки телефона в корпусе — под вопросом, вероятно не нужен при BYOD
- Для разработки нужен **отдельный физический Android-телефон** (эмулятор не умеет BLE)

## Периферия

**ESP32-S3-DevKitC-1 (модуль WROOM-1)** — полноразмерная плата с полной распиновкой, выбрана
сознательно вместо легаси-платы форкнутого проекта (папка `ESP32_S3_Mini_PythonFiles` —
просто унаследованное название, к плате отношения не имеет). Причина выбора и финальная
карта GPIO — в `PipBoy_BLE_Protocol_v0.2.md`, раздел 4.0. Три роли в одном МК:
1. BLE-мост к телефону
2. Сканер Wi-Fi для Гейгера
3. USB Host для чтения голодиска (bare-флешка на 4 магнитных pogo-контактах, не активное
   устройство — геркон/неодимовый магнит из старого дизайна больше не используются)

Риск: Wi-Fi scan может мешать BLE (общий радиотракт). План Б (не закупать заранее) — отдельный
ESP8266 только под Wi-Fi-сканирование, к ESP32-S3 по UART.

**Питание корпуса — автономное, отдельная схема от телефона** (roadmap, Phase C): LiPo (1S,
3.7В) → TP4056 с защитой → свой boost-преобразователь 3.7В→5В → 5V/VIN платы ESP32-S3
(тот же вход, что у USB). Тумблер питания — в разрыв между бустом и платой, не на цепи
заряда (заряжать можно при выключенном питании). Порт зарядки — свой у модуля TP4056
(USB-C/micro-USB), выведен наружу корпуса; USB-C самой платы ESP32-S3 остаётся внутренним,
только для прошивки. **Кнопка POWER из протокола — логический тумблер состояния
(`PipBoy_BLE_Protocol_v0.2.md`, раздел 3.1), не реальное включение электропитания** — ESP32
должен уже быть физически запитан и вещать BLE до того, как POWER что-либо переключает (это
же условие для пейринга — корпус должен быть включён питанием заранее). Ёмкость и физическое
место аккумулятора — под вопросом, зависит от свободного объёма в конкретной 3D-модели,
см. открытые вопросы.

**Гейгер на ESP32 (прошивка PipBoy)** — только мгновенное чтение (сканирует сети
`R10/R20/R50` — уточнить, есть ли ещё `R100` как более высокий уровень, см. открытый вопрос
ниже; есть сигнал → уровень по силе сигнала на аналоговом вольтметре + пьезодинамик, нет
сигнала → тишина/ноль). Без памяти, без накопления дозы, без сброса на уровне самого
сканера — это не меняется, ESP32 остаётся тупым мгновенным датчиком. Индикация — аналоговый
вольтметр (ШИМ+RC-фильтр с ESP32-S3), не степпер (степпер — только если делать отдельный
физический циферблат часов).

**Официальный датчик радиации игрока (отдельный проект «Игровая радиация») — НЕ часть
PipBoy.** Отдельное носимое устройство на игроке (ESP8266 + LED), сканирует те же сети,
копит дозу и обнуляется **только мастерами через сеть-сброс** `R0`/`RAD0` (в исходном
документе название сети противоречиво, не уточнено). Это авторитетный источник дозы для
игровых правил — PipBoy на него никак не влияет и не может обнулить.

**Счётчик радиации в STATS (приложение PipDroid) — отдельная, дополнительная фича, не
конфликтует с официальным датчиком.** Это удобство для игрока: раз на PipBoy уже есть
Гейгер, приложение само копит дозу по тем же мгновенным показаниям `GEIGER:<0-255>` от
ESP32 (накопление — на стороне приложения, не прошивки) и **обнуляется самим игроком
кнопкой на экране**, когда захочет. Не авторитетный источник для игровых правил — просто
личный трекер поверх Гейгера, параллельно официальному датчику, а не вместо него.

## Протокол связи телефон ↔ ESP32-S3

**Вариант А** (принят после находки существующего кода): не кастомный GATT-сервис, а
расширение уже готовой архитектуры автора PipDroid — **Nordic UART Service (NUS)**.

- Service UUID `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`, TX `...0003` (ESP32→телефон, notify),
  RX `...0002` (телефон→ESP32, write)
- Обмен — plain text команды, конвенция `КЛЮЧ:ЗНАЧЕНИЕ` для параметризованных, просто
  ключевое слово для остальных (как уже есть `STATS`/`ITEMS`/`DATA`)
- Уже работает в коде: 3 кнопки (GPIO 16/17/18, active-low, pull-up) на ESP32-S3
  (`ESP32_S3_Mini_PythonFiles/main.py`, класс `BLESimplePeripheral` определён прямо в файле,
  `ble_uart_peripheral.py` — НЕ используется, мёртвый референсный файл), опрос раз в 350мс,
  шлёт строку **каждый цикл, пока кнопка держится** (не событие изменения)
- На телефоне: `MainActivity.kt`, `menuChangeBLE()` — `when(menu){"STATS"->...}`.
  `BluetoothGattCallback.onCharacteristicChanged` уже работает
- Пейринг — ручной: MAC + UUID вводятся в настройках, хранятся в SharedPreferences
  (`bluetoothMAC_SPKey`, `bluetoothSUUID_SPKey`, `bluetoothRUUID_SPKey`, `bluetoothWUUID_SPKey`)
- Путь телефон→ESP32 (`writeCharacteristic()`/`sendBLEText()`) есть в коде, но не проверено,
  привязан ли реально к какому-то действию в UI — **проверить перед тем как полагаться на него**

**Новые команды (см. полный список в `PipBoy_BLE_Protocol_v0.2.md`):**
`POWER`, `ENCBTN`, `ENC:±N`, `GEIGER:<0-255>`, `HOLOTAPE:1/0`, `RADIOFREQ:<val>` (ESP32→телефон);
`RADIOPWR:1/0`, `RADIOFREQ:<val>`, `HOLOTAPE:LIST`, `HOLOTAPE:READ:<n>`
(телефон→ESP32). Голодиск-чанкинг (`HOLOTAPE:DATA:...`) — черновой, ждёт теста throughput.
Список неполный и устаревает по ходу работы — актуальный источник истины по командам и
GPIO всегда `PipBoy_BLE_Protocol_v0.2.md`, этот файл только даёт общую картину.

**Что нужно поправить в прошивке при добавлении новых команд:**
- Назначить GPIO под Power/энкодер (свободные, избегать 0/3/45/46 — strapping-пины, и 19/20 —
  USB D+/D-, если ESP32-S3 держит нативный USB Host для голодиска)
- Для нового функционала — слать **по изменению состояния**, не по опросу каждые 350мс
  (иначе `ENC:+1` будет дублироваться). Существующие STATS/ITEMS/DATA не трогать, они рабочие
- Задействовать `on_rx` — сейчас просто пишет пришедшую строку в `vars.sentVALUE`, дальше
  никак не используется, нужно распарсить и реально дёрнуть периферию

## Архитектурный принцип: тематизация интерфейса

**Любой новый или дорабатываемый экран должен краситься текущей темой оформления**
(Green/Amber/White/Blue, `playerUIColour_SPKey` в SharedPreferences) — кнопки, иконки,
заголовки, основной текст и прочие подходящие элементы, а не жёстко зашитым цветом одной
темы. Это не опция, а прямое следствие того, что тема вообще существует как фича приложения.

Установлено на примере кнопок/текстов экрана выбора режима и мастера PipBoy 2000/3000
(roadmap, косметические правки): изначально были жёстко зелёными, поправлено на тематизацию.

**Как это устроено в коде** (`MainActivity.kt`):
- Активность применяет **единственный раз** при старте (`onCreate`, `theme.applyStyle(...)`)
  один из `Theme.PipDroid.{Green,Amber,White,Blue}UI` — тема на лету **не переприменяется**,
  activity не пересоздаётся при смене цвета в Settings
- Поэтому все элементы, которые должны краситься динамически (в т.ч. при живой смене темы в
  Settings), красятся **не через саму Activity-тему**, а вручную кодом, читая
  `sharedPreferences.getInt(playerUIColour_SPKey, 0)` — есть 2 параллельных, оба рабочих пути:
  - Уже существовавший до правок: `applyAppTheme()`/`applyBackgroundResource()`/
    `applyTextColor()`/`applyProgressDrawable()` — точечные списки конкретных View
  - Добавлен в этой правке: `currentWizardAccentColor()` — короткий helper, возвращает
    `themeGreen`/`themeAmber`/`themeWhite`/`themeBlue` по индексу; кнопки красятся через
    `button.backgroundTintList = ColorStateList.valueOf(accent)` поверх **нейтральных**
    (белых/прозрачных) drawable-заготовок, тексты — через `setTextColor(accent)`
- Готовое исключение, ничего не делать: **`ImageView.tint`** уже подхватывает тему сам —
  `Theme.PipDroid.{Green,Amber,White,Blue}UI` определяет `android:tint`, и ImageView без
  явного своего tint наследует его через дефолтный стиль. Проверено на иконке Vault-Boy в
  мастере (`pipboy_3nv.png`, обычный статичный PNG без своей логики) — уже была тематизирована
- **backgroundTintList на кнопках исторически был источником бага** (AppCompat сам тянул
  тон от `colorPrimary` темы поверх кастомного drawable, см. историю правок кнопок) — теперь
  это осознанно используемый, а не побочный механизм, но `android:backgroundTint="@null"`
  в стиле/XML не работает на этом AGP/AAPT2 (см. окружение разработки ниже), тон снимается/
  ставится только кодом

## В работе: единый Settings + новая шапка (ветка `app-header`)

Спека собрана целиком заранее (roadmap, "Новая шапка + единый Settings — UX-спецификация") —
осознанно, по итогам этапа мастера PipBoy 2000/3000, где спека несколько раз менялась по ходу
разработки. Реализация Settings разбита на контрольные точки — каждая коммитится и проверяется
на устройстве отдельно, не одним огромным коммитом:

1. **(Сделано)** Убрать MENU-виджет переключения вкладок внутри Settings + свести три
   физические копии разметки (`<include layout="@layout/layout_tab_settings">` в
   STATS/ITEMS/DATA) к одной, со всем, что от этого технически неотделимо — оказалось, что
   сведение количества XML-инстансов и консолидация Kotlin-кода, который на них ссылается
   (точки входа/выхода, RadioGroup-листенеры формата даты/цвета темы, блок инициализации
   полей, применение темы `applyBackgroundResource`/`applyTextColor`/`applyScrollBar`, и —
   как выяснилось по ходу дела — Bluetooth Setup подэкран, тоже висевший на тех же трёх
   копиях) нельзя честно разделить на отдельные шаги — компилятор не даст оставить XML без
   Kotlin-кода, который её ждёт. Изначально планировали как 2-3 разных контрольные точки
   (MENU+вход/выход, тема+инициализация, Bluetooth отдельно), по факту это один неделимый
   шаг, включивший всё сразу. Проверено на устройстве: единый экран открывается одинаково из
   STATS/ITEMS, Bluetooth Setup подэкран внутри работает, закрытие (X) возвращает на
   исходный экран.
2. **(Сделано)** Новое поле "Игровой год" в Settings (`et_settings_year_value`, дефолт 2276,
   между World Map Scaling и Date Formats) + правка логики даты: `Calendar.getInstance()`
   как есть (реальные месяц/день/время), но поле `YEAR` перед форматированием подменяется
   пользовательским значением из `gameYear_SPKey` — правка в клоке DATA-шапки/попапа часов
   на радио (единственные два места, где `Calendar` уходил в `SimpleDateFormat`), не
   переделка самого механизма форматирования. Проверено на устройстве: при игровом годе
   2300 дата показывает "...00" вместо реального "...26", месяц/день/время не изменились.

Settings закрыт. Дальше — сама новая шапка (roadmap, "Новая шапка + единый Settings —
UX-спецификация"), тоже по контрольным точкам:

3. **(Сделано)** Каркас 3-зонной структуры — сразу для STATS/ITEMS/DATA, не пилотом на
   одном разделе: при реализации выяснилось, что перенос строки 2 (второй уровень) наверх
   технически не завязан на конкретный раздел вообще (`setupBottomBar()` как переключала
   три существующих инстанса `inc_layout_tab_stats/items/data_bottom` по видимости, так и
   переключает — только физически они теперь лежат в новом `row2_constraintLayout` под
   строкой 1, а не в отдельной зоне внизу экрана), поэтому ограничивать пилот одним STATS
   смысла не было. Было: строка 1 (10% экрана) = имя раздела + живые данные вперемешку
   (`layout_tab_stats_title.xml` и аналоги, теперь удалены), строка 2 (низ, тоже 10%) =
   второй уровень. Стало: строка 1 (`layout_header_toplevel.xml`, один общий инстанс) =
   переключатель STATS/ITEMS/DATA (без RADIO — отдельный пункт 5) + шестерёнка Settings
   слева + BLE-индикатор справа; строка 2 = второй уровень, без изменений в логике, просто
   переехал; низ (`bottom_constraintLayout`) = контекстная живая панель — у STATS свой
   инстанс (`layout_header_bottom_stats.xml`, LVL/HP/AP/XP), у ITEMS/DATA общий
   (`layout_header_bottom_datetime.xml`, дата/время с игровым годом из п.2 — ITEMS раньше
   показывал Wg/HP/DT/CAPS в шапке, по спеке это не переехало, "игровой показатель не
   определён"). Строка 2/нижняя панель — это готовые XML `<include>` (как и раньше было
   для второго уровня), не программное построение через `addView()`: раздел-специфичного
   контента там мало и он известен заранее (в отличие от списка найденных BLE-устройств в
   `addPairingDevice()`, для которого приём был предложен изначально), плодить программную
   генерацию ради 3-5 кнопок не оправдано. Готового ассета шестерёнки в проекте не было —
   нарисована как простой vector drawable (`ic_settings_gear.xml`). BLE-индикатор
   (`ic_ble_status.xml`) переиспользует `PipBoyBleService.isConnected()`/
   `onConnectionStateChanged`, состояние подключён/нет передаётся альфой иконки, не сменой
   drawable. Долгое нажатие для фонарика (было 3 копии слушателя на `tv_title_data` в
   каждой из старых шапок) стало одним слушателем на корне `layout_header_toplevel.xml`.
   По ходу дела всплыла и была исправлена регрессия: суммарная высота-под-шапку выросла с
   20% экрана (10%+10%) до изначально запланированных 30% (20%+10%), из-за чего контент
   некоторых экранов (например ITEMS → Weapons, блок STR/DPS/WG/VAL/CND) стал обрезаться
   снизу — пересчитано на 24% (строка1+строка2 по 8% каждая, нижняя панель 6%), край
   отступов (`layout_marginTop=12dp`, рассчитанный на старую, более высокую шапку) в новых
   `layout_header_bottom_*.xml` уменьшен до 2dp. Проверено на устройстве во всех трёх
   разделах: переключение STATS/ITEMS/DATA тапом по строке 1, второй уровень, нижняя
   панель (включая игровой год в дате ITEMS/DATA), шестерёнка (открывает тот же общий
   Settings), BLE-индикатор (тускнеет при DISCONNECTED), General/Misc-экраны с их старыми
   точечными кнопками Settings — работают наравне с новой шестерёнкой, не убраны (не было
   необходимости трогать 3 дополнительных layout-файла ради строгой дедупликации точек
   входа, когда несколько путей к одному и тому же экрану не создают риска рассинхрона,
   в отличие от того, что было с тремя копиями самого Settings).
4. **Вынос RADIO в top-level.** 4-я кнопка строки 1, у неё нет строки 2 (пустой контейнер/
   скрыт), выбор — через физический тумблер радио (`RADIOPWR:1` от ESP32, протокол раздел

## Открытые вопросы

- Название сети-сброса для датчика дозы игрока: `R0` (по коду) vs `RAD0` (по тексту исходного
  документа) — противоречие не разрешено, датчик игрока всё равно отдельный проект
- Формула пересчёта RSSI → `GEIGER:<0-255>` — заглушка, калибровать на реальном железе
- Путь телефон→ESP32 через `writeCharacteristic()` — проверить, привязан ли к чему-то в UI
- Нужен ли вообще pogo-pin разъём зарядки в корпусе при BYOD
- Сколько игроков одновременно на площадке — не зафиксировано, важно для смет отдельного
  проекта «Игровая радиация» (не для этого репозитория)
- **Шрифт `res/font/monofonto.ttf` не содержит кириллицы вообще** (проверено `fontTools` —
  0 кириллических глифов в cmap), для русского текста Android молча подставляет системный
  шрифт — на заголовках (крупный кегль, капс) разница в начертании с латиницей особенно
  заметна, шрифт "разваливается". Решено чинить **основательно, отдельной веткой, во время
  работы над локализацией** (roadmap, "Видение приложения") — не точечным `textStyle="bold"`
  на заголовках сейчас. Нужен файл моноширинного шрифта с кириллицей в похожем "блочном"
  техно-стиле (кандидаты не выбраны, ждём файл от пользователя, как и со звуком ошибки)
- **Ёмкость и физическое место LiPo-аккумулятора питания корпуса** — не определены, зависят
  от свободного объёма в конкретной 3D-модели после размещения платы ESP32-S3/FM-модуля/
  пого-контактов/телефона. Вероятный кандидат по месту — Cuff 1 (roadmap, раздел 5), но не
  обмерян под это отдельно
